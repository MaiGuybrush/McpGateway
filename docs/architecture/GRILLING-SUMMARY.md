## 🎯 GRILLING 關鍵發現

### ** 發現 #1：設定檔驅動的致命缺陷 **

**原始設計**：
- Tool 名稱、描述、參數描述全放 `tools-config.json`
- 程式碼只負責實作邏輯
- 啟動時驗證，遺漏描述 → 服務無法啟動

**Grilling 暴露的問題**：
1. **雙重維護地獄**：新增參數時，C# record 與 JSON 設定檔都要改
2. **無編譯期檢查**：忘記更新設定檔 → 運行期才知道
3. **部署阻塞**：描述文字更新變成"破壞性變更"
4. **違反直覺**：描述文字不應該影響服務可用性

**建議方案**：
- **混合方案（ADR-003 選項 C）**：程式碼內聯預設描述 + 設定檔可選覆寫
- **緩解措施**：啟動驗證從 fail-fast 改為 warning（ADR-004 選項 B）

**決策阻塞點**：必須在編碼前確定 ADR-003

---

### ** 發現 #2：安全模型的單一故障點 **

**原始設計（NFR-5）**：
> "下游 API 認證資訊集中於 Tool Facade 管理，不暴露給 AI 用戶端"

**Grilling 暴露的問題**：
1. **單一故障點**：Tool Facade 被入侵 = 所有下游 API 認證洩漏
2. **無權限模型**：所有 AI Agent 權限相同
3. **無稽核日誌**：無法追蹤誰呼叫了什麼
4. **秘密管理**：認證資訊存哪裡？設定檔？Vault？

**建議方案**：
- **MVP（ADR-006 階段 1）**：
  - API Key 認證（識別 Agent）
  - 環境變數儲存認證（進程注入）
  - 完整稽核日誌（含 PII 遮蔽）
- **長期（ADR-006 階段 3）**：OAuth 2.0 + ABAC + Vault

**決定性問題**：安全是「可以稍後再做」還是「MVP 必須」？

---

### ** 發現 #3：測試策略完全缺失 **

**原始設計**：完全無提及測試

**Grilling 暴露的問題**：
1. **如何測試單個 Tool 邏輯？** Mock HttpClient？
2. **如何測試 MCP 協定層？** 需要啟動真實 MCP Server？
3. **如何確保設定檔描述與程式碼同步？** 契約測試？
4. **如何測試 LLM 行為？** 自動化 Prompt 測試？

**影響**：
- 無法安全重構
- 無法保證變更不破壞既有功能
- 生產環境缺陷風險高

**建議測試策略**：

```
測試金字塔：

┌──────────────────────────┐  
│  E2E 測試 (MCP 完整鏈)    │ 1-2 個關鍵路徑
├──────────────────────────┤
│  整合測試 (Tool + HTTP)   │ 每個 Tool
├──────────────────────────┤
│  單元測試 (邏輯)          │ 欄位轉換、投影
├──────────────────────────┤
│  契約測試 (Schema)        │ CI 自動
└──────────────────────────┘
```

**具體措施**：
1. **單元測試**：每個欄位轉換邏輯獨立測試
2. **整合測試**：使用 WireMock 模擬 Ocelot
3. **契約測試**：啟動時驗證參數覆蓋率（ADR-004）
4. **E2E 測試**：完整 MCP 呼叫鏈，至少 1-2 個關鍵 Tool
5. **Prompt 測試**：自動化測試 LLM 選擇正確 Tool 與填參

**決策**：測試策略必須在開發前確立，否則無法保證品質

### **發現 #4：量化 ROI 的缺失**

**原始假設**：
> "機械式轉換 LLM 錯誤率高，手動封裝提升正確率"

**Grilling 質疑**：
1. **數據在哪裡？** 錯誤率具體數值？測試了多少案例？
2. **提升多少？** 手動封裝後正確率從 X% → Y%？
3. **成本效益？** 開發成本 + 維護成本 vs 錯誤率降低價值？

**關鍵問題**：

**Q1: 錯誤率是否真的高到需要獨立服務？**
```
選項 A：機械式轉換 + 更好 Prompt
- 成本：幾天工程師時間優化 Prompt
- 效果：可能達到 90%+ 正確率

選項 B：獨立 Tool Facade 服務
- 成本：數人月開發 + 持續維護
- 效果：未知，假設 95%+

選項 B 比 A 好 5%，值得嗎？
```

**Q2: "多功能共享端點"問題有多普遍？**
- 受影響的 API 佔比多少？
- 能否重構下游 API（長期解決方案）vs 封裝層（短期緩解）？

**Q3: ChatGPT Function Calling 直接呼叫 Ocelot 是否可行？**
- 現代 LLM（GPT-4, Claude）理解 REST API 的能力已大幅提升
- 給予清晰的 Swagger + Prompt，可能直接工作
- 省下一整個服務的維護

**建議**：
- **PoC Phase 1**：機械式 OpenAPI→MCP 轉換 + Prompt 工程
- **PoC Phase 2**：手動封裝 2-3 個關鍵 Tool
- **比較指標**：正確率、呼叫成功率、開發成本
- **基於數據決策**：Phase 1 若達到 >90% 正確率，還需要 Phase 2 嗎？

   - 評估團隊 C# 能力

   - 測試不是「可選」，是「必須」
   - 至少定義單元測試與整合測試策略
   - 考慮使用 TDD

### **盡快行動（Do Soon）**

2. **安全審核**
   - 與安全團隊審核 ADR-006
   - 確定秘密管理解決方案
   - 定義稽核要求

3. **建立 PoC**
   - 不要直接進入全面開發
   - 用 2-3 週驗證核心假設
   - 基於數據決定下一步

### **長期關注（Watch）**

1. **版本控制**
   - 當 Tool 數量 > 20 時，需要版本機制
   - 現在建立約束（所有變更必須向後相容）

2. **管理介面**
   - Tool 數量 > 50 時，手動管理設定檔不可行
   - 提前規劃 Tool Catalog 需求

3. **效能優化**

   - 考慮快取策略（下游 API 響應）
